# macOS Remote Control-only Upgrade — Spec #657

Status: **source-only reliability hardening** after the v0.1.50 real Mac failed upgrade; the existing public v0.1.50 Release and Worker installer are unchanged. Source changes alone do not authorize a new Release, Worker repin or real-device operation.

## User-visible contract

An owner-approved permanent Mac already connected to RCA may initiate an upgrade from a Remote Control `run_command` without typing in a local Terminal. The initiator uses the **public Worker-pinned HTTPS source**, with the published explicit `--remote-upgrade` action (not an unverified branch/checkout). The public script checks the exact architecture, SHA-256-pinned immutable Agent asset, reviewed `macos-local.sh` source and correct original Worker endpoint. The existing `--upgrade` remains interactive. The v0.1.50 first real attempt failed and the original `v0.1.49-rc.4` permanent Agent was recovered with its identity unchanged; this source-only hardening does not repair or upgrade that device.

## One-shot dispatch

The verified new package's `macos-local.sh remote-upgrade` stages its reviewed bundle under a private per-operation directory, validates the already-permanent device's UID, owned LaunchAgent/CLI, approved identity, connection generation with matching live LaunchAgent PID, endpoint, original receipts, no intentional STOP, no unresolved switch journal, no existing remote operation and a strictly forward target version/architecture (official stable succeeds its rc; downgrade/same version forbidden). It creates an idempotency marker and dispatches exactly one **same-user `launchctl bootstrap` job** with a private per-operation plist (`RunAtLoad=true`, `KeepAlive=false`, `LaunchOnlyOnce=true`) running the bundled Node/manager from the durable stage, outside the managed Agent Shell. The launcher returns `status=launched` and the unique operation ID. It is not an upgrade-success receipt. Unknown dispatch state is not automatically retried.

The independent job tolerates a bounded (up to ~7.25 seconds) `busy` freeze response while its initiating Remote Control Shell drains. It never retries an unknown freeze, switch, or remote command; if operations remain busy it records `needs_attention` and requires inspection.

The detached job requires the same owner UID, exact operation record and launchd job label with its own PID, with launchd as its parent, before allowing noninteractive confirmation. This does not weaken the ordinary terminal requirement. It reuses the current native manager's pin validation, active-work freeze, side-by-side candidate, signed WSS post-switch verification and rollback/Unknown behavior. No new pairing, cloud grant override, production data mutation or persistent updater is created.

A private per-operation result is either `connected_observed` or `needs_attention`; keep records for audit and check the new cloud device session, version, unchanged device ID, signed WSS, LaunchAgent and original SQLite receipts independently. The job is one-shot: the previously used `launchctl submit` was observed to restart a failed task hundreds of times on the owner Mac, because launchd expressly keeps submitted programs alive after failure. The new per-operation plist must be verified on native macOS CI to execute once even after nonzero exit. An inactive registration may remain; it is not a persistent process. Any abandoned/uncertain state remains blocked for explicit reconciliation. Do not manually delete pending locks, guess an outcome or replay old commands.

## Mandatory gates

1. Existing native macOS ARM64 and Intel hosted CI, plus Linux/Windows regression, must pass the exact Agent candidate. Include rejection of false launchd job PID/context, missing key, forged/expired approval, owner STOP, bad endpoint/source/OS, existing upgrade marker, duplicate operation, busy sessions and uncertain activate/rollback.
2. Release new native macOS Agent assets via the **existing protected Agent GitHub Actions** after separate owner authorization. Only after immutable SHA readback, update the **existing RCA Worker installer** to pin this Release and expose `--remote-upgrade`; Worker release needs separate production authorization.
3. For first hop, do **not** rely on the installed rc.4 CLI having a new switch. The future Worker-served, independently SHA-validated temporary bootstrap dispatches the one-shot launchd job using the newly published helper. The launch does not claim completion.
4. Only after approved real Mac execution, independently verify original identity, new version and signed WSS + SQLite receipts. Previously waived physical login/sleep/fault/Intel tests remain Waived; non-waived Gatekeeper/TCC/APFS negatives are not implied Pass.

Cross-platform precedent: `docs/remote-shell-upgrade.md` implements the same independent task principle using `systemd-run --user` (Linux) or one-shot same-user Scheduled Task (Windows). Mac uses launchd; no `upgrade_agent` MCP tool or additional long-lived service.

## Failed real-device transaction: evidence-preserving reconciliation gates (#660)

The original `v0.1.50-darwin-arm64` operation `097c1008-5498-4a1d-ae70-b7eff25253cd` ended `needs_attention` with `switch_pending` and `active.json` still present. Its original permanent `v0.1.49-rc.4` LaunchAgent and signed WSS were later independently restored under the **same** device ID. The failed, auto-restarting submitted job was booted out *once* under a separate, exact-target owner authorization. This proves service recovery, **not** successful v0.1.50 installation or automatic recovery of the original upgrade transaction.

Any future reconciliation is a distinct owner-authorized **device state change**; the current source fix does **not** perform it. Before allowing it:

1. Independently identify the exact device, UID, operation ID, the one archived `context.json` source/target, `result.json=needs_attention`, `active.json` and `switch.json`. Require owner-private regular files (no links), and verify that `switch.json.previous` **exactly** matches the currently installed original plist and original generation, that the pinned CLI still points to the original version, the old LaunchAgent process/PID is live, the signed WSS device ID and generation match, and original receipts still exist. Keep Unknown receipts non-retryable; do not use `sqlite3` to bypass the live Agent's exclusive receipt lock.
2. Confirm the **exact** failed detached job is absent from launchd on multiple separated read-only observations, and its error log has stopped growing; no second command, task, service transition, or owner STOP is pending. Treat any error/unknown result as blocked, not as proof of absence. Do not touch the old permanent LaunchAgent.
3. Preserve the original switch/active/context/result/log contents and exact paths in an owner-private, immutable-identity audit record with verified digests before considering any change to admission gates. Do **not** rewrite `result.json` to success, replay the operation, delete the staged candidate, rotate the key or change the original receipt records. Record recovery as **manual old-service restored, upgrade failed/unknown**, not as `connected_observed`.
4. Only after explicit, separate owner approval and an independently reviewed *idempotent* reconciliation implementation may the *specific* obsolete `switch.json` and `active.json` admission markers be released, with intermediate/crash-unknown handling and post-change signed-WSS/CLI/receipt validation. Unexpected data, missing evidence or ambiguous file states must remain blocked. The prior `v0.1.50` operation must never be replayed; a later upgrade requires a new reviewed version and authorization.

These gates deliberately require no new service, database, automatic retry or general-purpose cleanup interface. Preserve the failed incident evidence on the owner Mac until owner authorization and acceptance of that exact transition.
